# MAX Bloom — Спецификация проекта (v2, финальная)

> Трек: «Эффективный бизнес». Дедлайн онлайн-этапа: 30 сентября, 12:00 МСК.
> Этот документ — единственный референс для разработки. Старая версия (`MAX_BLOOM_SPEC.md`) не используется.

---

## 1. Проблема

**Пользователь:** самозанятый/ИП, ведущий закрытое платное сообщество (канал/чат) в MAX — эксперт, тренер, репетитор, консультант.

**Проблема:** сейчас такой человек принимает оплату вручную (переводы на карту, риск по 115-ФЗ), сам сверяет, кто оплатил, сам кикает неплательщиков, часто не выставляет чек (риск по ФЗ-54). Это ручной труд и юридический риск, а не отсутствие способа продавать вообще.

**Решение:** бот в MAX, который принимает оплату по СБП, автоматически выдаёт доступ, автоматически кикает при неоплате, автоматически формирует чек.

Покупатель — не отдельный герой продукта, а часть сценария предпринимателя.

## 2. Позиционирование сценария (порядок важен)

```
[Кабинет крейтора: тариф + привязка канала]
        │
        ▼
[Крейтор делится ссылкой на тариф]
        │
        ▼
[Покупатель: карточка → оплата СБП] ──▶ [Бот выдаёт инвайт]
        │
        ▼
[Дашборд крейтора: выручка, подписчики, платежи]
```

Кабинет крейтора — первый и главный экран продукта. Витрина/каталог — вспомогательный элемент, не самоцель.

## 4. MoSCoW

**Must have:**
- Бот: онбординг крейтора, создание тарифа, привязка канала (`bot_added`)
- Дашборд крейтора: выручка, активные подписчики, список платежей
- Мини-апп покупателя: карточка сообщества + тариф + оплата СБП (ЮKassa sandbox)
- Webhook ЮKassa → обновление статуса платежа → подписка ACTIVE → генерация одноразового токена (`invite_tokens`) → отправка прокси-ссылки `https://bloom.example/i/{token}` в личку
- Redirect-эндпоинт `/i/{token}`: проверка токена (не найден/`USED`/истёк → страница «Ссылка устарела»; иначе → `status=USED` + 302 на `communities.invite_link`)
- Обработка ошибки оплаты (рабочая ветка, не мок)
- Шедулер: ежедневный кик по `expires_at` **и** сверка участников канала с активными подписками (см. п.8)

**Should have:**
- Напоминания за 3 дня / в день истечения подписки
- Несколько тарифов на одно сообщество
- Деактивация тарифа
- Экспорт статистики крейтора в Excel
- Перевыпуск токена по запросу («Мои подписки» → «Прислать ссылку ещё раз»): если `subscriptions.status = ACTIVE` — бэкенд создаёт новую запись в `invite_tokens` (старый токен уже `USED`/истёк, повторно использовать нельзя) и присылает новую прокси-ссылку. Закрывает тупик «токен истёк, а подписка активна»

**Could have:**
- Лента-заглушка из 5 демо-кейсов (раздел 3), явно помечена как демоданные

**Won't have (сознательно, зафиксировать в README):**
- Персональные рекомендации, поиск по интересам
- Лайки, отзывы, рейтинги
- Способы оплаты кроме СБП
- Публичный маркетплейс с массовым скроллом каталога
- Трекинг конверсии по источникам ссылок (требует отдельной таблицы логирования кликов — избыточно для срока сдачи, тариф получает одну простую ссылку без меток источника)

## 6. База данных

Таблицы: `users`, `communities`, `subscription_plans`, `subscriptions`, `payments`.
Полная DDL и описание полей — см. `10_database.md`. Плюс четыре дополнения ниже (не меняют существующие таблицы, кроме двух новых полей).

Ключевые принципы:
- ФЗ-152: только `max_user_id`, никаких телефонов/email
- ФЗ-161: `UNIQUE(idempotency_key)` на платежах
- Атомарность: платёж + подписка в одной `@Transactional`

**Важное уточнение по `users.role`:** это метка «с чего человек начал» для аналитики и дефолтного экрана, **не право доступа**. Один и тот же пользователь может одновременно быть крейтором (`communities.creator_id`) и покупателем (`subscriptions.user_id`) — схема это не ограничивает, и запрещать не нужно. Главное меню бота (`/start`) всегда показывает обе опции — «Хочу продавать» и «Смотреть каталог» — независимо от прошлого выбора пользователя. Не гейтить доступ к покупке или к созданию бизнеса на основании `role`.

**Дополнение 1 — `communities.invite_link` (TEXT, nullable):** кэш статической ссылки канала (`Chat.link`), получаем один раз при привязке (`bot_added`) через `GET /chats/{chatId}`, чтобы не дёргать MAX API при каждой оплате. Если ссылка в MAX была вручную заменена админом — обновляем кэш при следующей ошибке редиректа (см. п.8.1).

**Дополнение 2 — новая таблица `invite_tokens`:** реализует настоящую одноразовость поверх статической ссылки MAX (см. п.8).

| Поле | Тип | Описание |
|---|---|---|
| `id` | `BIGSERIAL` | PK |
| `token` | `UUID` UNIQUE | значение в прокси-ссылке `/i/{token}` |
| `subscription_id` | `BIGINT → subscriptions.id` | к какой подписке относится |
| `status` | `VARCHAR(16)` | `ACTIVE` / `USED` |
| `expires_at` | `TIMESTAMPTZ` | `created_at + 24h` |
| `created_at` | `TIMESTAMPTZ` | момент генерации (после `payment.succeeded` или повторного запроса) |
| `used_at` | `TIMESTAMPTZ`, nullable | момент перехода по ссылке |

Индекс: `UNIQUE(token)` — быстрая проверка на redirect-эндпоинте.

**Дополнение 4 — правило удаления тарифа:** `subscription_plans` поддерживает только деактивацию (`is_active = false`) как способ убрать тариф с продажи. Физическое удаление строки допустимо приложением только при 0 связанных `subscriptions` и `payments` — иначе теряется история платежей (ФЗ-54) и шедулер перестаёт видеть действующих подписчиков для кика. FK `subscriptions.plan_id` и `payments.plan_id` — без `CASCADE` (по умолчанию Postgres блокирует удаление при наличии ссылок), это дополнительная защита на уровне БД поверх проверки в приложении.

**Дополнение 3 — `users.self_employed_confirmed` (BOOLEAN, default `false`):** декларативное подтверждение крейтора перед активацией первого тарифа («подтверждаю, что зарегистрирован как самозанятый/ИП/ООО»). Не проверка, а зафиксированное согласие нести ответственность. Реальная верификация через открытый API ФНС (проверка НПД по ИНН) — вне MVP, условие масштабирования (см. п.9).

## 8. Ограничения MAX API и механика доступа

- Бот **не может** добавлять пользователей в чат программно
- В MAX API нет метода для создания одноразовых/ограниченных по времени ссылок — только статическое поле `link` объекта `Chat` (`GET /chats/{chatId}`), одна на канал, без встроенного контроля переходов
- `POST /chats/{chatId}/members`: **ограничен с 9 сентября 2026, полностью удалён с 30 сентября 2026** (день дедлайна сдачи). Не использовать вообще
- Кик — `DELETE /chats/{chatId}/members?user_id={userId}&block={true|false}` (документировано, подтверждено). Требует у бота права `add_remove_members` — это техническое имя в API, в интерфейсе MAX может отображаться иначе («Управление участниками»)
- Список участников — `GET /chats/{chatId}/members`
- Проверка собственных прав бота в чате — `GET /chats/{chatId}/members/me`, поле с массивом прав включает `add_remove_members`, если бот может кикать
- Только webhook в проде (`POST /subscriptions`), long polling — не для сдачи
- Мини-апп открывается только из бота, не как отдельный сервис
- Базовый URL: `platform-api2.max.ru`, авторизация — заголовок `Authorization: <token>`
- Сертификат Минцифры обязателен в truststore
- Модерация заявок на вступление в приватный канал — функция уровня приложения MAX, одобряется вручную человеком-администратором. У ботов нет метода для чтения/одобрения очереди заявок. Крейтор может включить её сам как дополнительный ручной контроль, но это вне автоматизации нашего продукта

### Механика "одноразовой" ссылки — реализуем сами, поверх статической `Chat.link`

MAX не умеет выдавать одноразовые/истекающие ссылки — эмулируем это на своём бэкенде:

1. При привязке канала (`bot_added`) один раз получаем `Chat.link` через `GET /chats/{chatId}` и кэшируем в `communities.invite_link`
2. После `payment.succeeded` бэкенд создаёт запись в `invite_tokens`: свой `token` (UUID), `status = ACTIVE`, `expires_at = now + 24h`
3. Пользователю в бот отправляется **своя** ссылка `https://bloom.example/i/{token}`, не `Chat.link` напрямую
4. Redirect-эндпоинт `/i/{token}`:
   - токен не найден / `status = USED` / `expires_at` истёк → страница «Ссылка устарела» с кнопкой вернуться в бота за новой
   - иначе → `status = USED`, `used_at = now`, HTTP 302 на `communities.invite_link`

Даёт настоящую одноразовость и срок жизни без нестандартных вызовов к MAX — вся логика на своей стороне.

**Честная оговорка (в README):** после редиректа реальная ссылка MAX оказывается в адресной строке браузера — теоретически её можно скопировать оттуда и передать дальше в обход токена. Это барьер от случайной пересылки сообщения бота, а не крипто-защита. От намеренного обхода защищает следующий пункт.

### Страховка — сверка участников (Must have)

Шедулер дополнительно сверяет фактических участников канала с активными подписками:
1. `GET /chats/{chatId}/members`
2. Для каждого `user_id`: есть ли `subscriptions.status = ACTIVE` на этот `community_id`
3. Если нет — `DELETE /chats/{chatId}/members`

Закрывает случай, когда токен всё же обошли.

## 8.1. Известное ограничение — фиксировать в README, не реализовывать

Если бота удалили из канала или лишили прав администратора — вызовы `GET/DELETE /chats/{chatId}/members` вернут ошибку. В MVP это не чинится (`Won't have`), но не должно падать молча:
- бот отвечает пользователю: «Не получилось выдать доступ, поддержка уже уведомлена»
- ошибка логируется на бэкенде

Также сюда относится случай, если админ вручную заменил `Chat.link` в приложении MAX — наш кэш в `communities.invite_link` устареет. Обнаруживаем по ошибке при редиректе, обновляем кэш повторным запросом `GET /chats/{chatId}` — не блокирующая доработка, но упомянуть в README как известное ограничение.

## 9. Критерии жюри → что показываем

| Критерий | Вес (онлайн) | Чем закрываем |
|---|---|---|
| Работоспособность MVP | 30% | Сквозной сценарий: тариф → оплата → доступ → кик, без разрывов |
| Корректность интеграций | 20% | Mini App ↔ Spring Boot ↔ MAX Bot API ↔ ЮKassa webhook, валидация `initData` (HMAC-SHA256) |
| Архитектура и код | 20% | Слоистая архитектура, индексы в БД, Docker Compose |
| Безопасность и ФЗ РФ | 10% | ФЗ-152, ФЗ-54, ФЗ-161 (см. п.6) |
| Стабильность/ошибки | 10% | `@ControllerAdvice` + RFC 7807, обработка ошибки оплаты, `@Transactional` |
| Документация | 10% | README, `docker compose up`, Swagger, `openapi.yaml`, `DATA-API.yaml` |
| Платформенный бонус | +0.15 | MAX SDK (Haptic, ThemeParams, MainButton), deep linking |
| Потенциал масштабирования | 35% | 5 демо-кейсов из разных сфер + явные условия адаптации (что меняется/остаётся), включая переход от декларативного подтверждения самозанятости к реальной проверке через API ФНС |
| Пользовательская ценность | 25% | Крейтор запускает продажи за 3 минуты без разработчика |
| UX/UI | 20% | Дашборд крейтора — главный экран; покупательский поток — минимум шагов без тупиков |
| Обоснованность решения | 15% | Один сценарий от начала до результата, без лишних функций |

Не заявлять юнит-экономику и размер рынка числами без источника — риск по критерию «обоснованность».
