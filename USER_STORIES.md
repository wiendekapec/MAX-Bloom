# MAX Bloom — User Stories

> Референс для разработки. Приоритеты (Must/Should/Could) соответствуют MoSCoW из `MAX_BLOOM_SPEC_v2.md`, п.4.
> Роли: **Крейтор** (предприниматель/самозанятый), **Покупатель**, **Система** (бот/шедулер/бэкенд).

---

## EPIC 1 — Онбординг крейтора

### US-1.1 [Must] Выбор роли при первом запуске
**Как** новый пользователь бота, **я хочу** увидеть выбор «Хочу продавать» / «Хочу покупать» при любом первом запуске, **чтобы** начать нужный поток независимо от того, как я попал в бота.

**Acceptance criteria:**
- `/start` **без параметров** — основной путь, всегда показывает выбор «💼 Хочу продавать» / «🛍 Смотреть каталог», **независимо от того, что пользователь выбирал раньше** (не эксклюзивный выбор — один человек может быть и крейтором, и покупателем)
- `?start=business` — необязательный шорткат для маркетинговых ссылок: сразу открывает ветку продавца, минуя экран выбора (не единственный вход в поток продавца)
- При выборе «Хочу продавать» — экран про самозанятость со ссылкой на npd.nalog.ru
- Пользователь сохраняется в `users` с `role = BUSINESS` при первом действии продавца (не при простом просмотре). `role` — метка для аналитики, не ограничивает доступ к другой ветке

### US-1.2 [Must] Создание бизнес-профиля
**Как** крейтор, **я хочу** указать название и описание своего сообщества, **чтобы** оно отображалось в карточке для покупателей.

**Acceptance criteria:**
- Бот последовательно запрашивает: название, описание, категорию (кнопками)
- Категория — одна из фиксированного списка (`business`, `education`, `fitness`, `tech`, `services`)
- Создаётся запись в `communities` с `creator_id` текущего пользователя

### US-1.3 [Should] Форма создания профиля в мини-аппе вместо чат-опроса
**Как** крейтор, **я хочу** заполнить название, описание и категорию одной формой в мини-аппе, **чтобы** не проходить пошаговый опрос в чате и не терять прогресс при опечатке.

**Acceptance criteria:**
- Мини-апп открывается по кнопке из бота, форма с полями: название, описание, категория (селект)
- Валидация полей на клиенте (обязательность, длина) до отправки
- Отправка создаёт ту же запись `communities`, что и в US-1.2 — эндпоинт общий, отличается только источник данных
- Заменяет US-1.2 при наличии времени; если не успеваем — остаётся чат-вариант

### US-1.4 [Must] Подтверждение статуса самозанятого (заглушка)
**Как** крейтор, **я хочу** явно подтвердить, что я зарегистрирован как самозанятый/ИП, **чтобы** платформа зафиксировала моё согласие нести ответственность за легальность приёма платежей.

**Acceptance criteria:**
- Перед активацией первого тарифа (не раньше) показывается обязательный чекбокс: «Подтверждаю, что зарегистрирован как самозанятый/ИП/ООО»
- Без подтверждения тариф не может получить `is_active = true`
- Сохраняется в `users.self_employed_confirmed` (BOOLEAN, по умолчанию `false`)
- **Это декларация, не проверка.** Реальная верификация через открытый API ФНС (проверка постановки на учёт НПД по ИНН) — не в MVP, фиксируется как условие масштабирования в презентации

### US-2.1 [Must] Создание тарифа
**Как** крейтор, **я хочу** задать название, цену и период тарифа, **чтобы** покупатели могли на него подписаться.

**Acceptance criteria:**
- Бот запрашивает название, цену (число ₽), период (7/30/90 дней или «разово»)
- «Разово» сохраняется как `period_days = 0`
- Создаётся запись в `subscription_plans`, `is_active = true`

**Примечание:** так же, как US-1.2/US-1.3, эта форма — сильный кандидат на перенос в мини-апп (несколько полей = MAX сам рекомендует форму, а не чат-опрос). Приоритет Must — за рабочий чат-вариант; перенос в форму — Should have, см. US-1.3.

### US-2.2 [Should] Несколько тарифов на одно сообщество
**Как** крейтор, **я хочу** добавить второй тариф (например, «Pro»), **чтобы** предложить покупателям выбор.

**Acceptance criteria:**
- Из дашборда доступна кнопка «Добавить тариф»
- Новый тариф привязывается к тому же `community_id`
- В карточке сообщества у покупателя показываются все активные тарифы

### US-2.3 [Should] Деактивация тарифа
**Как** крейтор, **я хочу** скрыть тариф с продажи, **чтобы** новые покупатели его не видели, но действующие подписчики не потеряли доступ.

**Acceptance criteria:**
- `is_active = false` не влияет на существующие `subscriptions`
- Деактивированный тариф не отображается в карточке для новых покупателей
- В дашборде тариф помечен как «Скрыт»
- **Физическое удаление тарифа (`DELETE` строки) доступно только если по нему 0 записей в `subscriptions` и 0 в `payments`.** Если есть хоть одна — кнопка «Удалить» не показывается вообще, доступна только «Деактивировать». Это не UX-ограничение, а защита данных: FK на `subscriptions.plan_id`/`payments.plan_id` не должен быть `CASCADE` — иначе удаление тарифа стирает историю платежей (нарушение хранения данных для чеков ФЗ-54) и «ослепляет» шедулер, который перестаёт видеть действующих подписчиков для последующего кика

## EPIC 3 — Привязка MAX-канала

### US-3.1 [Must] Привязка канала к тарифу
**Как** крейтор, **я хочу** добавить бота администратором в свой канал, **чтобы** система могла выдавать и отзывать доступ автоматически.

**Acceptance criteria:**
- Бот показывает инструкцию: добавить @MaxBloomBot админом с правом `add_remove_members` (в интерфейсе MAX может называться «Управление участниками»)
- Система ловит событие `bot_added`, сохраняет `chat_id` в `communities.max_chat_id`
- После привязки — проверка `GET /chats/{chatId}/members/me`: если `add_remove_members` отсутствует в правах бота, крейтору показывается предупреждение «Дайте боту право на управление участниками, иначе кик неплательщиков не сработает»
- Бот сразу запрашивает `GET /chats/{chatId}`, кэширует `Chat.link` в `communities.invite_link`
- Крейтору приходит подтверждение «Канал привязан» с названием канала

### US-3.2 [Should] Персональная ссылка на тариф
**Как** крейтор, **я хочу** получить готовую ссылку на тариф, **чтобы** делиться ей в разных каналах продвижения.

**Acceptance criteria:**
- Бот выдаёт ссылку вида `https://max.ru/MaxBloomBot?start=plan_{id}`
- Переход открывает мини-апп сразу на карточке этого тарифа
- Трекинг конверсии по источникам — вне MVP (см. `Won't have` в спецификации)

## EPIC 4 — Покупка и оплата

### US-4.1 [Must] Просмотр карточки тарифа
**Как** покупатель, **я хочу** увидеть описание сообщества и доступные тарифы, **чтобы** выбрать подходящий.

**Acceptance criteria:**
- Открывается мини-апп с карточкой: название, описание, аватар, список активных тарифов с ценой и периодом
- Данные приходят по контракту из `14_env_and_api_contract.md`

### US-4.2 [Must] Оплата через СБП
**Как** покупатель, **я хочу** оплатить тариф в 1 клик, **чтобы** не вводить данные карты вручную.

**Acceptance criteria:**
- Нажатие MainButton «Оплатить через СБП» вызывает `HapticFeedback.impactOccurred`
- Бэкенд создаёт запись в `payments` (`status = PENDING`, `idempotency_key = UUID`) и вызывает `POST /v3/payments` ЮKassa (sandbox)
- Открывается страница подтверждения ЮKassa (QR/диплинк)

### US-4.3 [Must] Обработка успешной оплаты
**Как** система, **я хочу** обработать webhook `payment.succeeded`, **чтобы** активировать подписку и выдать доступ.

**Acceptance criteria:**
- Проверка подписи webhook и `idempotency_key` (повтор — `200 OK` без повторной обработки, ФЗ-161)
- `payments.status = SUCCEEDED`, создаётся запись `subscriptions` (`status = ACTIVE`, `expires_at = now + period_days`)
- Генерируется `invite_tokens` (см. US-5.1), обновляется `subscribers_count` сообщества

### US-4.4 [Must] Обработка ошибки оплаты
**Как** покупатель, **я хочу** видеть понятную причину, если оплата не прошла, **чтобы** попробовать снова или обратиться в поддержку.

**Acceptance criteria:**
- При `payment.canceled` / таймауте бот присылает сообщение с причиной и кнопками «Попробовать снова» / «Написать в поддержку»
- «Попробовать снова» создаёт новый платёж с новым `idempotency_key`, не переиспользует старый
- `payments.status = CANCELED`

## EPIC 5 — Выдача доступа

### US-5.1 [Must] Генерация одноразовой прокси-ссылки
**Как** система, **я хочу** выдать покупателю одноразовую временную ссылку, **чтобы** реальная ссылка канала не расходилась бесконтрольно.

**Acceptance criteria:**
- После `payment.succeeded` создаётся запись `invite_tokens`: `token` (UUID), `status = ACTIVE`, `expires_at = +24h`
- Покупателю в личку приходит ссылка `https://bloom.example/i/{token}`, не сама ссылка канала

### US-5.2 [Must] Переход по прокси-ссылке
**Как** покупатель, **я хочу** перейти по ссылке и попасть в канал, **чтобы** получить доступ к купленному контенту.

**Acceptance criteria:**
- Если токен `ACTIVE` и не истёк — `status = USED`, `used_at = now`, HTTP 302 на `communities.invite_link`
- Если токен не найден / `USED` / истёк — страница «Ссылка устарела» с кнопкой вернуться в бота

### US-5.3 [Should] Перевыпуск токена
**Как** покупатель, **я хочу** запросить новую ссылку, если старая истекла, **чтобы** попасть в канал без повторной оплаты.

**Acceptance criteria:**
- В боте пункт «Мои подписки» → «Прислать ссылку ещё раз»
- Доступен только если `subscriptions.status = ACTIVE` для этого пользователя
- Создаётся новая запись `invite_tokens`, старая остаётся `USED`/истёкшей

## EPIC 6 — Контроль доступа (система)

### US-6.1 [Must] Ежедневный кик по истечению подписки
**Как** система, **я хочу** ежедневно проверять `expires_at`, **чтобы** автоматически исключать неплательщиков.

**Acceptance criteria:**
- Шедулер запускается ежедневно в 00:00, выбирает `subscriptions` где `expires_at < NOW() AND status = ACTIVE`
- Вызывает `DELETE /chats/{chatId}/members`, обновляет `status = EXPIRED`
- Крейтору не требуется никаких действий

### US-6.2 [Must] Сверка участников канала с активными подписками
**Как** система, **я хочу** сверять фактических участников канала со списком активных подписок, **чтобы** исключать тех, кто попал в канал без оплаты (утёкшая ссылка).

**Acceptance criteria:**
- Шедулер вызывает `GET /chats/{chatId}/members`
- Для каждого участника без `subscriptions.status = ACTIVE` на этот `community_id` — `DELETE /chats/{chatId}/members`
- Владелец канала (`creator_id`) исключён из проверки

### US-6.3 [Should] Уведомление перед истечением
**Как** покупатель, **я хочу** получить напоминание за 3 дня и в день истечения, **чтобы** успеть продлить подписку.

**Acceptance criteria:**
- За 3 дня до `expires_at` — сообщение с кнопкой «Продлить»
- В день истечения (если не продлил) — повторное сообщение
- «Продлить» ведёт на тот же чекаут, что и первичная покупка (US-4.2)

## EPIC 7 — Дашборд крейтора

### US-7.1 [Must] Обзор выручки и подписчиков
**Как** крейтор, **я хочу** видеть выручку и число активных подписчиков, **чтобы** понимать состояние бизнеса без ручного подсчёта.

**Acceptance criteria:**
- Главный экран мини-аппа крейтора показывает: суммарную выручку за период, число `subscriptions.status = ACTIVE`
- Данные обновляются при каждом открытии дашборда (не кэшируются статично)

### US-7.2 [Must] История платежей
**Как** крейтор, **я хочу** видеть список последних платежей, **чтобы** сверять поступления без запроса выписки у ЮKassa.

**Acceptance criteria:**
- Список из `payments` с датой, суммой, статусом, отсортирован по `created_at DESC`
- Отображается платформенная комиссия отдельной колонкой

### US-7.3 [Should] Экспорт в Excel
**Как** крейтор, **я хочу** выгрузить статистику в `.xlsx`, **чтобы** передать бухгалтеру или сохранить для себя.

**Acceptance criteria:**
- Кнопка «Экспорт» на дашборде вызывает бэкенд-эндпоинт, который отдаёт `.xlsx` (платежи + подписчики за период)
- Во время генерации показывается индикатор загрузки

---

## EPIC 8 — Обработка ошибок и известные ограничения (система)

### US-8.1 [Must] Ошибка при недоступности канала
**Как** покупатель, **я хочу** получить понятное сообщение, если бот не смог выдать доступ, **чтобы** не остаться в неведении после оплаты.

**Acceptance criteria:**
- Если `GET/DELETE /chats/{chatId}/members` или редирект возвращают ошибку — бот отвечает «Не получилось выдать доступ, поддержка уже уведомлена»
- Ошибка логируется на бэкенде с `subscription_id` для ручного разбора
- Не реализуется автоматическое восстановление прав бота — фиксируется как известное ограничение в README
