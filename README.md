# 🌸 MAX Bloom

**Автоматизация платных подписок для самозанятых и ИП в MAX.**

Бот + мини-приложение: крейтор создаёт тариф, привязывает канал — покупатели платят через СБП, бот автоматически выдаёт доступ и кикает неплательщиков.

> **Трек:** «Эффективный бизнес» · Хакатон MAX
> **Интеграция с ЮKassa используется в тестовом режиме (sandbox). Реальные списания не происходят.**

## 1. Проблема и решение

**Пользователь:** самозанятый/ИП, ведущий закрытый платный канал в MAX.

**Сейчас:** принимает оплату вручную (переводы на карту), сам сверяет кто оплатил, сам кикает неплательщиков, часто не выставляет чек → риск по ФЗ-54.

**С MAX Bloom:**

| | Сейчас | С MAX Bloom |
|---|---|---|
| Приём оплаты | Реквизиты в личке | Оплата в 1 клик по СБП |
| Учёт подписчиков | Таблица/память | Автоматический журнал в БД |
| Кик неплательщиков | Вручную | Шедулер ежедневно |
| Чеки (ФЗ-54) | Часто забывают | Автоматически через ЮKassa ОФД |

## 3. Сквозной сценарий

### Крейтор
1. `/start` в боте → «💼 Кабинет продавца»
2. Онбординг: подтверждение статуса самозанятого
3. Название, описание, категория сообщества
4. Создание тарифа: название, цена, период
5. Добавить бота администратором в канал с правом `add_remove_members`
6. Бот ловит `bot_added`, кэширует `Chat.link`, выдаёт ссылку на тариф
7. Открыть Дашборд → выручка, подписчики, платежи, управление тарифами

### Покупатель
1. Переход по ссылке `https://max.ru/MaxBloomBot?start=plan_42`
2. Мини-апп → карточка сообщества → выбор тарифа → Оплатить через СБП
3. Страница ЮKassa sandbox → подтверждение
4. Webhook `payment.succeeded` → бэкенд: подписка `ACTIVE` + `invite_tokens`
5. Бот отправляет `https://bloom.example/i/{token}` в личку
6. Переход по ссылке → HTTP 302 → `communities.invite_link` → вступление в канал
7. При истечении: шедулер кикает + уведомление «Продлить»

### Проверка пошагово (для жюри)
```
1. Открыть бота @MaxBloomBot → /start
2. Кнопка «💼 Кабинет продавца»
3. Пройти онбординг, создать тариф (цена: 1 ₽ для sandbox)
4. Добавить бота в тестовый канал администратором
5. Скопировать ссылку на тариф из бота
6. Открыть ссылку (другой аккаунт / браузер) → оплатить (карта 5536913776836354)
7. Получить invite-ссылку в боте
8. Перейти по ссылке → вступить в канал
9. Дождаться 00:00 UTC → убедиться, что шедулер кикает истёкших
```

## 4. Запуск через Docker

```bash
git clone <repo>
cd bloom

# Скопировать и заполнить переменные
cp .env.example .env
nano .env   # вставить MAX_BOT_TOKEN, YUKASSA_SHOP_ID и т.д.

# Запустить всё одной командой
docker compose up -d

# Проверить статус
docker compose ps
docker compose logs -f backend
```

| Frontend (nginx) | `80` |
| Backend (Spring Boot) | `8080` |
| PostgreSQL | `5432` |
| Swagger UI | `http://localhost:8080/swagger-ui.html` |

## 7. API и документация

- **Swagger UI:** `http://localhost:8080/swagger-ui.html`
- **OpenAPI спека:** [`frontend/openapi.yaml`](./frontend/openapi.yaml)
- **DATA-API контракт:** `DATA-API.yaml` (в корне, заполняется бэкендом)

Авторизация: заголовок `X-Init-Data` (initData от MAX Mini App SDK).
Бэкенд проверяет HMAC-SHA256 по алгоритму MAX Bot API.

Ошибки: RFC 7807 Problem+JSON (`application/problem+json`):
```json
{
  "type": "about:blank",
  "title": "Тариф недоступен",
  "status": 402,
  "detail": "Тариф деактивирован крейтором",
  "code": "PLAN_INACTIVE"
}
```

## 9. Ограничения (известные)

### MAX API
- **`POST /chats/{chatId}/members` удалён с 30.09.2026** — не используется. Вступление только через одноразовую прокси-ссылку `https://bloom.example/i/{token}`.
- Invite-ссылка одноразовая на нашей стороне, но после редиректа реальная `Chat.link` попадает в адресную строку. Это барьер от случайной пересылки, а не крипто-защита. Страховка — ежедневная сверка участников шедулером.
- Если бот потерял права администратора: вызовы `GET/DELETE /chats/{chatId}/members` вернут ошибку. Бот уведомит пользователя «Не получилось выдать доступ, поддержка уже уведомлена» + лог. Автоматического восстановления нет (Won't have MVP).
- FSM диалога бота хранится in-memory (`Map<userId, state>`). При рестарте сервиса — сбрасывается. Пользователь может начать заново с `/start`.

### ЮKassa
- Sandbox-режим. Реальный прод требует подключения ОФД и верификации магазина ЮKassa.

### ФЗ-152
- Хранятся только `max_user_id` (числовой ID), `first_name`, `username` — без телефонов и email.

## 10. Потенциал масштабирования

| Направление | Что меняется | Что остаётся |
|---|---|---|
| Верификация самозанятости | Добавить проверку по API ФНС (ИНН, НПД) | Декларация + `self_employed_confirmed` в схеме |
| Другие платформы (TG, ВК) | Адаптер Bot API + initData-верификация | Бизнес-логика, схема БД, ЮKassa |
| Рекуррентные платежи | ЮKassa `save_payment_method` + scheduled charge | Webhook-обработчик, шедулер |
| Публичный маркетплейс | Поисковый индекс, рейтинги, рекомендации | `communities` + `subscription_plans` таблицы |
| Аналитика по источникам | Таблица `link_clicks(source, plan_id, user_id)` | Тарифная ссылка, deep link механика |
| Массовые рассылки | Batch `POST /messages` с ограничением rate | `subscriptions` как список получателей |

Переход от декларативного подтверждения (`self_employed_confirmed = true`) к реальной верификации через открытый API ФНС (проверка постановки на учёт НПД по ИНН) — не требует изменения схемы БД, только добавления сервисного слоя.
